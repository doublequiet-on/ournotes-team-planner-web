# 普通与挑战综合力修复

网页版 v0.1.2 / 公开核心 v0.2.5 修复普通单人演出误用挑战活动参数加成的问题。受影响的是 v0.1.1 及以前网页、v0.2.4 及以前核心。旧单人分数可能被高估，跨评级时会影响 CP、活动 PT、商店 PT、循环场数和推荐排序，因此需要重新计算。

## 规则依据

固定游戏数据 `MasterText`（提交 `0f8644dd85b7c3d21794fb3f718e48773cd1cc60`）的 `Help_SubCategory_Description_140002` 明确写道：

> ※「パラメータボーナス」はチャレンジライブのみで発動します。

即参数加成仅在挑战演出中生效。原始说明可在基准解压后的 `research/2026-10-01/raw/MasterText.json` 查到；来源与文件 SHA-256 由同目录来源清单记录。

参考模型的 `model_reference/src/deck.rs` 为成员与 Snap 参数分别提供 `event` 开关。本项目之前只在 `PowerModel.music()` 切换挑战曲属性，初始化时却将活动参数加成用于所有模式。这是调用上下文错误。

| 项目 | 普通单人演出 | 挑战演出 |
| --- | --- | --- |
| 成员活动参数加成 | 不应用 | 按该成员匹配的活动效果应用 |
| Snap 活动参数加成 | 不加入支援率 | 加入对应 Snap 的支援率 |
| 乐曲属性 | 普通曲表 | 挑战曲表指定属性；未指定时回退普通曲表 |
| 活动 PT / 商店 PT 加成 | 按普通收益规则结算 | 按挑战收益规则结算 |

同队同曲时，只要存在适用的活动参数加成，两种模式的综合力就可能不同；不能把整队总值统一乘一个倍率。成员基础、Snap 支援以及依赖基础值的其他组件都要使用对应模式的数值。

## 实现与验证

`PowerModel` 按普通/挑战分别构建成员基础与 Snap 配对值，切换歌曲时选用对应模式，再计算乐曲、队长等组件。穷举与 CP-SAT 共用这个入口。详细核对函数 `calculate_selected_deck_power(..., ordinary=True)` 可单独计算普通演出。

`tests/test_power_modes.py` 使用合成养成，覆盖游戏规则文本、同队同曲同队长、反复切换模式、54 组详细与快速计算对照，以及两条搜索路径输出的模式归属。`browser/tests/check_power_modes.py` 从实际发布的固定 ZIP 加载模型运行检查。浏览器导出的 Top-3 队伍还会在原生端重算对应模式的综合力与得分。

此前的浏览器/原生一致性检查使用相同的旧模型，因此没有检出双方共有的模式错误。之前的普通收益截图也没有绑定这支队伍，不能证明普通综合力正确。本次验证游戏规则与代码回归，没有新增单人综合力实机截图对照。

## 升级

保存输入后刷新网页，确认显示 v0.1.2 或更新版本，再计算。卡库仍保存在原网址；更新前建议导出备份。模型源码哈希变化会让旧计算缓存失效，续算可恢复输入并重新计算。旧导出结果不会被自动改写。

计算包的请求地址包含网页版本号，避免新版页面命中旧版公式包的 HTTP 缓存。发布时仍需递增 `browser/package.json` 中的版本号。

源码归档升级不会自动替换用户已经安装的 Windows EXE。
